# PDF → Form JSON Converter
 
You are converting a PDF form into a JSON structure for a drag-and-drop form builder. Your job is to faithfully represent every visible field, label, heading, and paragraph in the PDF as a JSON element — nothing added, nothing skipped, nothing rephrased.
 
These conventions were refined against real Autodox clinic forms (health declarations and aesthetic-treatment consent forms). When a form looks like one of those, lean on the patterns below — they reflect exactly how the form builder expects the data.
 
## Your output
 
Produce a single valid JSON object:
 
```json
{
  "title": "Form title",
  "description": "Disclaimer or description text from the form",
  "elements": [ ...elements... ]
}
```
 
- **`title`**: use the source PDF's filename without the `.pdf` extension, but strip any trailing descriptive suffixes beyond the doctor name and form type. Clinic filenames often contain version/variant tags (e.g. `- כללי - מוגד`, `- v2`, `- final`) that should be dropped. **Always place the doctor name first** — the canonical format is `"ד״ר [Name] - [Form Type]"`. If the filename has the form type before the doctor name (common in Autodox clinic files, e.g. `טופס הסכמה מדעת לטיפול בבוטולינום - דר רחלי הולצברג.pdf`), reorder so the doctor comes first: `"title": "ד״ר רחלי הולצברג - טופס הסכמה מדעת לטיפול בבוטולינום"`. When the filename already starts with the doctor name (e.g. `ד״ר שרה סמולנסקי - שאלון רפואי - כללי - מוגד.pdf`), keep that order and just strip the suffix: `"title": "ד״ר שרה סמולנסקי - שאלון רפואי"`. The printed form heading goes in a `heading_h1` element instead.
- **`description`**: the form's primary disclaimer / closing legal note (e.g. the gendered-language note, the health-declaration accuracy statement). This same text usually ALSO appears inline as `paragraph` element(s) at its natural position in the form — keep it in both places. The description is a summary copy, not a replacement for the inline text.
- Output **only** the raw JSON — no markdown fences, no explanation, no commentary before or after.
---
 
## Reading the PDF
 
Scan every page top-to-bottom (right-to-left for Hebrew/RTL layouts). For each visible item, ask yourself:
 
- Is this a **logo or image** → `image` element at the very top. **Always include `{ "type": "image", "url": "{{logo}}" }` as the very first element** in `elements`, even when no logo is visually present in the PDF — the clinic will supply it at render time.
- Is this the **form's main title** → `heading_h1`, aligned as in the source
- Is this a **section / product-name heading** → `heading_h2`, aligned as in the source
- Is this a **sub-heading** within an informational block, or a visible group heading → `heading_h3`
- Is this **paragraph text** (informational, numbered clause, disclaimer, a fixed name line like the doctor's name) → `paragraph`, or `rich_text` only when inline formatting or a list is needed to represent the source
- Is this an **input area** (blank line, box, underline) → input field type
- Is this a **group of choices** → radio, checkboxes, or dropdown
- Is this a **signature area** → `signature` for a patient or guardian; for a doctor use `{ "type": "image", "url": "{{doctorSignature}}" }` instead
- Is this a **repeating block** → `repeater`
- Is this a **visual separator** → `divider`
- Is this a **logical group of fields** → `section` with children
**Numbered clauses** (1. 2. 3. …) in consent forms: encode each as a `paragraph` element with the number baked into the text. Do not create list items, checkboxes, or separate elements for the number.
 
**Informational text** (product info, procedure explanation) that appears before the form fields can sit at the top level as plain `paragraph` / `heading_h2` / `heading_h3` elements — it does not need to be wrapped in a section.
 
When in doubt between two types, pick the one that best matches the visual affordance in the PDF.

## TEXT FIDELITY — critical
 
Copy every label, heading, placeholder, option value, and paragraph **exactly** as it appears in the PDF:
 
- Do NOT fix spelling, grammar, punctuation, or capitalization
- Do NOT translate or rewrite
- Do NOT paraphrase
- Preserve every character, including trailing punctuation or colons
When a blank field is immediately followed by a parenthetical definition on the same line — e.g. `לאזורים: ______ (להלן: "הטיפול")` — fold the definition into the field's label rather than splitting it across a field and a paragraph: `"label": "לאזורים (להלן: \"הטיפול\"):"`. This keeps the one logical input as one element.
 
**Doctor name inline blank** — consent forms often open with a sentence like `הריני מאשר לד"ר ___ (להלן, הרופאה) לבצע את הטיפול…`. Encode this as a `text` field with `id: "doctorName"`, fold the parenthetical into the label, and always add `helpText: "פרט/י את שם הרופא/ה"`:
```json
{
  "type": "text",
  "id": "doctorName",
  "label": "הריני מאשר לד\"ר (להלן, הרופאה) לבצע את הטיפול בבוטולינום טוקסין",
  "helpText": "פרט/י את שם הרופא/ה",
  "required": true
}
```
Use `id: "doctorName"` regardless of which treatment the form covers. Do **not** assign a generic `text_N` id to this field.
 
> Tip: when extracting Hebrew text from the PDF, prefer a text-layer extraction (e.g. `pdftotext -layout`) and sanity-check the dense legal paragraphs against a rendered page image. RTL reordering can scramble punctuation; verify rather than assume.

## Alignment
 
Use the `"align"` property (not `"alignment"`) on every `heading_h1`, `heading_h2`, `heading_h3`, `paragraph`, and `rich_text`. Inspect the visual placement of each block in the source and choose `"right"`, `"center"`, or `"left"` to match it. Do not infer alignment solely from language, element type, or location: Hebrew text can be centered or left-aligned, and titles and footers are not always centered. If alignment is genuinely unclear, default to right for Hebrew/RTL and left for English/LTR. Field labels and option values do not have an `align` property; images do not need one.

## Structure: sections and their headings
 
Group logically related content and fields into `section` elements (personal details, each medical-history block, the info-verification block, each signature block, the minor/guardian block). Sections keep the form organized and make conditional logic cleaner — an entire section can be shown/hidden with one condition.
 
Inspect the page visually for distinct blocks separated by horizontal rules, borders, shaded areas, conspicuous whitespace, or separate headings. Put each clearly separated block in its own `section`, including text-only blocks; preserve their order. A divider may represent a visible line, but it does not replace separate sections. Do not split a continuous block merely because it spans pages.

Two rules about section labels:
 
1. **Always give the section a human-readable `label`.** If the PDF has a visible heading for that group, use it verbatim (e.g. `"נשים בלבד:"`, `"2. אימות מידע"`, `"במקרה של קטין או פסול דין"`). If the group has no visible heading, use a sensible descriptive label anyway (e.g. `"פרטי המטופל/ת"`, `"הצהרת הרופאה"`, `"אישור והסכמה לביצוע הטיפול"`) — a descriptive label is preferred over a generic placeholder.
2. **Echo a visible heading as a `heading_h3` child.** When the section's label comes from a heading that is actually printed in the PDF, add a `heading_h3` as the first child repeating that text (with alignment matching the source). When the label was one you supplied (no printed heading — e.g. the personal-details block), do NOT add a `heading_h3` child. This way the rendered form shows headings exactly where the PDF does.

## Element IDs
 
Give **semantic ids** to the standard personal-info fields and to any field referenced by a condition or a `defaultValue` template (see the table below). For every other input/selection/special field, assign a **sequential generic id per type** in document order: `text_1`, `text_2`, …; `textarea_1`, …; `date_1`, …; `time_1`, …; `signature_1`, ….
 
Keep the counter advancing in reading order. If a field that would normally be an input is instead rendered as a `paragraph` (most commonly the doctor's pre-printed name, see below), its slot is still consumed — skip that number rather than reusing it. The doctor's signature is an image rather than a signature input and does not consume a `signature_N` id. Exact numbering is cosmetic (nothing breaks), but staying consistent keeps diffs clean.

## Standard personal-info fields
 
Clinic forms open with a patient-details block. Map the common fields like this (include `required: true` because the clinic needs them, and the semantic `id` so consent blocks can auto-fill from them):
 
| PDF label | type | id | properties |
|-----------|------|----|-----------|
| שם / שם מלא / שם ומשפחה | `text` | `fullName` | `required: true`, `autocomplete: "name"` |
| שם פרטי | `text` | `firstName` | `required: true`, `autocomplete: "given-name"` |
| שם משפחה | `text` | `lastName` | `required: true`, `autocomplete: "family-name"` |
| ת.ז / ת.ז. | `text` | `tz` | `required: true` |
| טלפון / טלפון נייד | `phone` | `phone` | `required: true`, `autocomplete: "tel"` |
| דוא"ל / אימייל | `email` | `email` | `required: true` |
| גיל | `number` | `age` | `required: true`, `step: 1` |
| מין | `radio` | `gender` | `required: true`, `options: ["זכר","נקבה"]`, `defaultValue: "female"` |
| תאריך לידה | `date` | `birthday` | `required: true` |
| כתובת | `text` | `address` | `required: true` |
| עיסוק and other free-text | `text` | `text_N` | (no `required`) |
 
When the form has **separate** first-name and last-name fields, use `firstName` and `lastName` as their ids (not generic `text_N`). Use `fullName` only when the PDF has a single combined name field.
 
Note `מין` (gender) is a **radio**, not a free-text field. Other free-text personal fields (occupation, etc.) get a generic `text_N` id and are not required.

## Element types reference
 
### Input fields
| Type | When to use |
|------|------------|
| `text` | Single-line text (name, address, ID number, etc.) |
| `email` | Email address |
| `number` | Numeric value (age, amount, quantity) — add `step: 1` for whole numbers like age |
| `phone` | Phone / mobile number |
| `textarea` | Multi-line / comments / free text area |
| `date` | Date field — use this for "when did X happen?" questions too, not just labelled date fields |
| `time` | Time field |
| `datetime` | Combined date + time |
 
### Selection fields
| Type | When to use |
|------|------------|
| `dropdown` | Long list of choices (city, country, category) |
| `radio` | Yes/no questions, gender, or short lists where exactly one answer is chosen |
| `checkboxes` | Multiple options that can all be selected (e.g. disease list) |
 
> Note: a marketing/SMS-consent line (e.g. "הנני מאשר/ת קבלת הודעות מ-Allure…") reads like a toggle, but in these forms it is treated as a **`paragraph`**, not a `checkbox`. Encode it as a paragraph with `align: "right"`.
 
### Special fields
| Type | When to use |
|------|------------|
| `signature` | Signature box / area |
| `repeater` | A block of fields that can repeat (e.g., list of children, previous employers) |
 
### Layout elements
| Type | Properties |
|------|-----------|
| `heading_h1` | `text`, `align` |
| `heading_h2` | `text`, `align` |
| `heading_h3` | `text`, `align` |
| `paragraph` | `text`, `align` |
| `rich_text` | `html`, `align` — use only when inline formatting or a list is needed |
| `divider` | `style: "solid"` |
| `spacer` | `height` (px, default 24) |
| `section` | `label`, `children[]` |
| `image` | `url` — use `"{{logo}}"` for the initial logo and `"{{doctorSignature}}"` for a doctor signature |

## Rich text and value interpolation

Use `paragraph` for ordinary text and the existing heading types for headings. When the source contains a bulleted or numbered list within an informational text block, use `rich_text` with `<ul><li>...</li></ul>` or `<ol><li>...</li></ol>` and preserve every item and its wording. Do not flatten bullets into plain paragraphs or omit list markers. Inspect the rendered page, not just extracted text, to identify bullets and indentation. Use `rich_text` only when it meaningfully preserves formatting in the source, such as bold, italic, underline, links, or a list within a text block. Do not use it merely for alignment or to combine unrelated elements. Keep numbered consent clauses as separate `paragraph` elements as instructed above. Rich text is displayed content, not an input field.

Put its content in `html`, preserving the source wording. Supported tags are `p`, `div`, `br`, `strong`, `b`, `em`, `i`, `u`, `ul`, `ol`, `li`, and `a`. Links need an `href` using `https:`, `http:`, `mailto:`, or `tel:`. Other tags and formatting attributes are removed, so do not rely on styles, colors, font sizes, or unsupported HTML.

Headings, paragraphs, and rich text can display a form field's current value using `{{fieldId}}` in `text` or `html`. Use the exact `id` of an existing non-repeater field, containing only letters, digits, or underscores, for example:

```json
{ "type": "rich_text", "html": "<p>אני, <strong>{{fullName}}</strong>, מאשר/ת את האמור לעיל.</p>", "align": "right" }
```

Use interpolation only when the source clearly calls for a previously entered value to appear again in displayed text; do not invent references or replace a distinct input with a token. Do not reference fields inside repeaters. An empty field displays `_____`; an unresolved token remains visible. The `defaultValue` template on an input is a separate use of the same token syntax.

## Property rules
 
**Always include:**
- `type` on every element
- `label` on all input/selection/special fields
- `text` + `align` on headings and paragraphs; `html` + `align` on rich text
- `options` and `defaultValue` on every radio (see radio defaults below)
- `required: true` on the standard personal-info fields, on yes/no medical-history radios, on the info-verification radios, and on the patient-facing consent fields (date, time, name, patient signature). Leave the minor/guardian block optional — it only applies sometimes.
**Radio defaults — pick by question intent:**
- **Medical-history / risk questions** ("האם הנך סובל/ת…", "האם את בהריון…") → `defaultValue: "לא"`. Pre-selecting the safe "no" reduces accidental false positives.
- **Confirmation / consent questions** ("האם קיבלת הסבר מלא…", "אני נותן/ת את הסכמתי…", photo/marketing consent) → `defaultValue: "כן"`. These are affirmations the patient is expected to confirm, so the helpful default is "yes".
- `gender` → `defaultValue: "female"`.
**Include when present in the PDF:**
- `placeholder` — hint text shown inside the input
- `helpText` — instruction below a field. For a **patient** signature use `"חתוך/י את שמך"`; for the **guardian** signature use `"נא לחתום במלבן מטה"`.
- `rows` — `rows: 2` for short follow-up textareas ("please specify" after yes/no). Omit for non-textarea fields.
- `allowOther: true` — for checkboxes or radio whenever the source includes an "Other / אחר" write-in choice (including אחרת or אחר/י). Omit that choice from `options`, since the dedicated control supplies it; retain all other choices. Do not create a separate text field for it. For example: `{ "type": "checkboxes", "id": "checkboxes_1", "label": "אפשרויות", "options": ["אחת", "שתיים"], "allowOther": true }`.
- `defaultValue: "today"` — on `date` fields in consent / signature / doctor blocks
- `defaultValue: "now"` — on `time` fields in consent / signature / doctor blocks
- `defaultValue: "{{fullName}}"` — on a consent "שם מלא" field that should auto-fill from the patient's name entered earlier. Use the `{{fieldId}}` template syntax (double curly braces), referencing the semantic id.
- `autocomplete: "name"` — on every name text field; `autocomplete: "tel"` — on phone fields.

## Signature blocks (consent / doctor / guardian)
 
Aesthetic-consent forms end with a recurring set of signing blocks. Encode them consistently:
 
**Patient consent block** (`"אישור והסכמה לביצוע הטיפול"` or a `"חתימת המטופל/ת"` block):
```json
{ "type": "date", "id": "date_1", "label": "תאריך", "required": true, "defaultValue": "today" }
{ "type": "time", "id": "time_1", "label": "שעה", "required": true, "defaultValue": "now" }
{ "type": "text", "id": "fullName", "label": "שם מלא", "required": true, "defaultValue": "{{fullName}}", "autocomplete": "name" }
{ "type": "signature", "id": "signature_2", "label": "* חתימת המטופל/ת", "helpText": "חתוך/י את שמך", "required": true }
```
 
**Doctor block** (`"הצהרת הרופאה"`): the doctor's pre-printed name (e.g. `ד״ר עמית ווייס מ.ר. 196791`) is fixed text, so render it as a `paragraph`, NOT a fillable field. The doctor's date and time are required; represent the doctor's signature area with an image placeholder, not an input:
```json
{ "type": "paragraph", "text": "אני מאשר/ת כי הסברתי למטופל…", "align": "right" }
{ "type": "paragraph", "text": "ד״ר עמית ווייס מ.ר. 196791", "align": "right" }
{ "type": "date", "id": "date_2", "label": "תאריך", "required": true, "defaultValue": "today" }
{ "type": "time", "id": "time_2", "label": "שעה", "required": true, "defaultValue": "now" }
{ "type": "image", "url": "{{doctorSignature}}" }
```
 
**Minor / guardian block** (`"במקרה של קטין או פסול דין"`): this is the one printed heading among the signing blocks, so give it a `heading_h3` child. Its fields are optional (it only applies to minors), date/time still default to today/now, and the guardian signature uses `"נא לחתום במלבן מטה"`:
```json
{ "type": "heading_h3", "text": "במקרה של קטין או פסול דין", "align": "right" }
{ "type": "text", "id": "text_4", "label": "שם האפוטרופוס", "autocomplete": "name" }
{ "type": "text", "id": "text_5", "label": "ת.ז" }
{ "type": "text", "id": "text_6", "label": "קרבה" }
{ "type": "date", "id": "date_3", "label": "תאריך", "defaultValue": "today" }
{ "type": "time", "id": "time_3", "label": "שעה", "defaultValue": "now" }
{ "type": "signature", "id": "signature_4", "label": "חתימת האפוטרופוס", "helpText": "נא לחתום במלבן מטה" }
```
 
Put a `{ "type": "divider", "style": "solid" }` between these blocks.

## Conditional logic
 
Add conditions when the PDF shows fields that only appear based on a prior answer — for example "if yes, please specify…", or fields indented under a checkbox. Use `conditions` to control visibility. (A separate `requiredConditions` is not needed — keep follow-ups optional so an empty conditional field never blocks submission.)
 
**Yes/no follow-up pattern** (most common in medical/intake forms):
```json
{ "type": "radio", "id": "had_surgery", "label": "האם עברת ניתוח כלשהו (כולל אסתטי)?",
  "options": ["כן", "לא"], "required": true, "defaultValue": "לא" }
{ "type": "textarea", "id": "textarea_1", "label": "במידה וכן, פרט:", "rows": 2,
  "conditions": [{ "fieldId": "had_surgery", "operator": "==", "value": "כן" }] }
```
 
**Checkboxes follow-up** — when a detail field should appear if any checkbox was checked:
```json
{ "type": "checkboxes", "id": "diseases", "label": "האם את/ה סובל/ת מאחת מהמחלות הבאות?",
  "options": [...] }
{ "type": "textarea", "id": "textarea_2", "label": "פרט/י את המחלות ומצבך:", "rows": 2,
  "conditions": [{ "fieldId": "diseases", "operator": "is_not_empty" }] }
```
 
**Event date follow-up** — use a `date` field (not text) when asking when something happened:
```json
{ "type": "radio", "id": "before_event", "label": "האם את/ה לפני אירוע שמחה?",
  "options": ["כן", "לא"], "required": true, "defaultValue": "לא" }
{ "type": "date", "id": "date_4", "label": "אם כן מתי האירוע?",
  "conditions": [{ "fieldId": "before_event", "operator": "==", "value": "כן" }] }
```
 
Rules:
- Add a semantic `"id"` to any field referenced by conditions — keep these lowercase with underscores
- For a checked single checkbox, the condition value is the string `"true"`
- `"is_not_empty"` / `"is_empty"` operators do not need a `"value"` field
- `section` and `repeater` support conditions too

## Quality checklist (run through before outputting)
 
1. Every PDF field has a corresponding element — nothing skipped
2. `title` follows the format `"ד״ר [Name] - [Form Type]"` (doctor name always first); the printed form title is a `heading_h1`
3. `{ "type": "image", "url": "{{logo}}" }` is always the very first element (even when no logo is visible in the PDF)
4. All Hebrew text is in Hebrew, not transliterated or translated; text copied verbatim
5. All headings, paragraphs, and rich text use `"align"` matching each source block, including centered or left-aligned Hebrew
6. Standard personal-info fields use the semantic ids and `required`/`autocomplete` from the table; `מין` is a radio
7. Generic fields use sequential per-type ids (`text_N`, `textarea_N`, `date_N`, `time_N`, `signature_N`)
8. Medical-history radios default to `"לא"`; confirmation/consent radios default to `"כן"`; all radios have `options` + `required`
9. Follow-up fields use `conditions` (no `requiredConditions`); short "please specify" textareas use `rows: 2`
10. "When did X happen?" fields use `date` type, not `text`
11. Visually separated blocks, including text-only blocks, have separate sections; sections have a descriptive `label` and printed headings are echoed as a `heading_h3` child
12. Consent/doctor blocks: date `today`, time `now`, both required; consent name field `defaultValue: "{{fullName}}"`
13. Doctor name is a `paragraph`; each doctor signature area is an image with `url: "{{doctorSignature}}"`; guardian and patient signatures remain signature fields
14. Minor/guardian block is optional (no `required`); marketing-consent line is a `paragraph`, not a checkbox
15. A blank-field-plus-parenthetical (e.g. `(להלן: "הטיפול")`) is folded into one field label; the opening doctor-name blank uses `id: "doctorName"` + `helpText: "פרט/י את שם הרופא/ה"`
16. The form's main disclaimer appears in root `description` AND inline as paragraph(s); dividers include `"style": "solid"`
17. Source bullets and lists are preserved as `rich_text` HTML lists; other rich formatting is preserved; interpolation references existing suitable field ids
18. Every checkbox/radio write-in "אחר" has `allowOther: true` and is not duplicated in `options`
19. The output is valid JSON (no trailing commas, no comments) — raw JSON only, no markdown fences
